一份 PiAgent 的折腾记录里，最值得留下的不是安装命令，而是这个报错：终端已经登录成功，Telegram 却还说找不到 API key。

原帖楼主从下午两点研究到晚上八点，先配置模型，再试 Web UI、记忆扩展和 Telegram 桥接。他说自己是科班出身但并非程序员，Pi 已经够满足他的使用需求。这是他的六小时体验，不是所有人都能在六小时内替换掉现有工具。

我把这份记录和另一条十章教程推荐放在一起整理。前者给出了具体卡点，后者提供了回头理解会话、事件和上下文的入口。先知道哪里会坏，再去看源码，问题往往更明确。

## 最先折腾的其实是供应商配置

主帖第一种方法是手写 `models.json`。示例除了地址、密钥和模型名，还有 API 类型、输入类型、上下文长度，以及流式用量、开发者角色等兼容选项。它解释了为什么“别人也用这个模型”不等于复制一行名字就能接上：客户端怎么发请求，和上游接受什么字段，还得对得上。

楼主后来改用 `@agegr/pi-web`，把模型、Skill 和插件的入口放在同一个界面里。这减少了手改配置文件的负担，不过界面能保存配置，仍不等于模型已经正常返回。

![Pi Agent Web 工作台，左下角有 Models、Skills 和 Plugins 入口，右侧显示会话与模型状态](/personal-site/media/posts/pi-agent-01.jpeg)

_来源：[实践帖 #1 楼](https://linux.do/t/topic/2571534/1)。图中的会话正文在原帖里就已模糊处理，保留的是工作台布局，不是任务结果。_

评论 [#48 楼](https://linux.do/t/topic/2571534/48) 补了一个更直接的入口：[Model Catalog](https://pi.dev/models) 的 “Show configuration”。与其猜字段，不如先找到相应模型的配置说明，再核对自己的供应商。原帖 [#55 楼](https://linux.do/t/topic/2571534/55) 还有人问同一模型在另一客户端能看图、在 Pi 里却不行；保存的讨论没有给出确定解法，因此不能把“文字聊天成功”当成图片输入也通过了。

## 插件能拼起来，但推荐名单不是验证报告

主帖装了头脑风暴、搜索、PDF 提取和记忆扩展，也引用过“一个模型规划、另一个模型执行”的用法。

![实践帖引用的模型分工讨论，上方说明规划与执行分别使用不同模型，下方是子任务终端界面](/personal-site/media/posts/pi-agent-03.jpeg)

_来源：[实践帖 #1 楼](https://linux.do/t/topic/2571534/1) 引用的另一条讨论截图。画面展示的是一位评论者的组合与任务状态，不是模型速度或成本的对照实验。_

把规划和执行分开，至少会多出一次交接：实施者要拿到目标、允许改哪些文件、如何判断完成。只交一个“帮我实现”的结论，前面的分析可能白做。截图里终端仍显示任务进行中，也不能据此说这套组合已经完成了项目。

原帖有两处写得很诚实：`pi-subagents` 和 `pi-hermes-memory` 都标了“只展示安装，等体验”。这两项应留在待试清单里。[#58 楼](https://linux.do/t/topic/2571534/58) 随后报告记忆越来越多时卡在写入、需要退出；这只是单个用户的反馈，却足以提醒读者，记忆功能还要测试长会话，而不是装完就算结束。

另一个有用的补充来自 [#23 楼](https://linux.do/t/topic/2571534/23)：记忆压缩阈值可以按模型上下文长度设置比例。同一个固定阈值用于不同窗口的模型，可能太早压缩。这里涉及的是配置思路，保存的帖子没有给出压缩前后质量的测试数据。

## “没登录”不一定是密钥填错了

Telegram 部分换了好几种方案。第一个每次启动 Pi 后都要手动连接，楼主觉得麻烦；常驻桥接则遇到下面的提示。

![Telegram 桥接提示找不到所选模型的 API key，发送 login 指令后又返回 Unknown command](/personal-site/media/posts/pi-agent-04.png)

_来源：[实践帖 #1 楼](https://linux.do/t/topic/2571534/1)。图里是错误消息和文档路径，没有展示密钥；它同时说明 Telegram 入口不一定支持 CLI 的全部指令。_

主帖引用的 [TelePi issue #10](https://github.com/benedict2310/TelePi/issues/10) 把一种失败原因说得很清楚：桥接进程启动时读取 `auth.json`，用户后来在 CLI 中登录，文件已经更新，常驻进程却仍持有旧凭据。于是同一台机器出现两种状态——新开的 CLI 能工作，早已启动的桥接不能。

issue 记录的临时办法是重启桥接，让它重新读取凭据。这个解释只适用于相应的凭据缓存问题，不是看到 “No API key” 就重启所有服务。先确认是哪一个模型、哪一个进程在报错，以及登录发生在进程启动之前还是之后，才能区分配置错误和旧状态。

楼主后来试了其他桥接，最终在更新后的主帖中选择 `pi-telegram-plus`，原因很具体：启动 Pi 后能自动连接，更合他的使用方式。这个选择值得参考，但不应写成今天所有插件的排名。模型切换工具也经历了当晚报错、作者跟进、次日反馈修复的过程，版本差一天，体验就可能不同。

## Pi 的吸引力和折腾成本，是同一件事

![实践帖引用的公开评论，评论者强调 Pi 可以自行添加功能，并附了一张终端截图](/personal-site/media/posts/pi-agent-02.jpeg)

_来源：[实践帖 #1 楼](https://linux.do/t/topic/2571534/1) 的引用图片。这是一种使用态度，不是“一小时一定能写好扩展”的承诺。_

评论 [#3、#4 楼](https://linux.do/t/topic/2571534/3) 把优势说成自定义，以及控制上下文加载的顺序和内容。相比一套拿来就用的成品，Pi 更适合想调工作方式的人；但模型配置、扩展兼容和后台进程也会变成自己要维护的东西。

如果要照着这份记录试，我建议先做一轮小检查：只接一个供应商，验证文字和实际需要的图片输入；只加一个扩展，比较启用前后的行为；CLI 通了再接 Telegram，测试新会话、重新登录和进程重启；记忆扩展单独跑长一点的会话，看压缩和写入会不会卡住。每一步留下版本号与错误消息，下次出问题时不必重新猜一遍。

想继续理解这些现象，可以接着读 [dg-ai-notes](https://github.com/buchidonggua/dg-ai-notes)。[教程推荐帖](https://linux.do/t/topic/2664634) 提到 Agent Loop、工具、消息、事件、会话和上下文，也有人质疑文字过于整齐。对我而言，最好的阅读题目就是回到这次故障：凭据何时读入，保存在哪个对象里，会话重建和进程重启各会刷新什么？能顺着源码回答它，比记住十章目录更有用。
