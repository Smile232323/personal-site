我收藏这篇帖子时，标题强调的是“10 章彻底搞懂 Agent 底层原理”。原帖给出的项目是 [dg-ai-notes](https://github.com/buchidonggua/dg-ai-notes)，并承诺每章同时讲概念、源码实现和设计原因，还提供 Web、Markdown、PDF 三种阅读方式。

这种介绍很容易让人直接收藏，却不一定真的学会。评论区大多数回复只是“先 mark”，也有人指出教程的 AI 味较重、回复过于整齐，还有人追问课程源码是否公开。对我来说，这些质疑不是噪音，而是判断教程质量的入口。

## 我用三层问题读每一章

一个 Agent 教程如果只解释名词，读完很快就会忘。我的阅读表固定写三列：

| 层次 | 必须回答的问题 | 不能用什么代替 |
| --- | --- | --- |
| 概念 | Agent Loop、工具、事件、会话、上下文分别解决什么问题？ | 一句“这是核心模块” |
| 实现 | 状态在哪里保存？事件怎样传递？错误怎样返回？ | 只有架构图没有代码 |
| 设计理由 | 为什么选这个边界？失败时怎样回滚？ | “为了更灵活、更高效” |

如果一章只有第一列，它更像术语导览；如果只有第二列，它可能是代码导读；只有三列都能互相对应，才接近可迁移的原理学习。

## 从 Agent Loop 开始，而不是从提示词开始

我会把一次可解释的 Agent 执行先写成一个小循环：

```text
读取当前状态
  → 生成计划或下一步动作
  → 请求一个受约束的工具
  → 检查返回值和副作用
  → 更新状态与上下文
  → 完成、重试，或停下来请求人工确认
```

这个循环里最容易被教程一笔带过的是“检查返回”和“主动停止”。如果工具失败，不能把整段错误日志原样塞回模型，让它继续猜；应该先判断是参数错、权限错、超时，还是外部服务已经发生了不可逆变化。超过重试次数或即将改动外部系统时，循环应该停止。

## 四个模块怎样互相约束

### 工具系统

工具不是给模型一把万能 shell。至少要有白名单、参数校验、超时、权限等级和结构化错误。读文件、运行测试、修改代码和发送外部请求，风险不应默认相同。

### 消息与事件

事件系统的价值是把“模型想做什么”和“系统实际做了什么”分开。计划、工具调用、工具结果、人工确认和失败原因都应有明确状态，否则审计时只能从一长段自然语言里猜过程。

### 会话管理

长期会话不能无限堆积聊天记录。我会把上下文分成当前任务、稳定规则、历史摘要和废弃信息，并给摘要标注来源和时间。压缩上下文后，未完成事项和安全边界不能丢。

### 审计层

审计不等于复制所有敏感内容。任务编号、工具名称、参数摘要、开始结束时间、结果状态和人工确认点已经足够定位大多数问题；真实密钥、私有文件全文和不必要的个人数据不应写入日志。

## 用固定任务验证教程是否真的能落地

读完概念后，我会准备五个小任务，而不是立刻做一个漂亮 Demo：

1. 只读检索：是否先读取规则，再输出来源？
2. 单文件修改：是否说明计划并运行最小验证？
3. 跨文件重构：是否能保持上下文边界，不乱改无关文件？
4. 测试失败修复：是否根据结构化错误定位，而不是重复尝试？
5. 外部操作：是否在发送、删除或发布前停下来请求确认？

这五类任务比“模型回答得像不像专家”更能暴露工作台的边界。教程里的代码如果没有覆盖失败、超时和回滚，我会把它记为概念示例，而不是生产方案。

## 如何识别“AI 味很重”

评论里说教程“AI 味重”，不能只凭句子顺不顺判断。我会看三个可观察信号：

- 每章标题都像“全面、彻底、从零到精通”，但没有对应的失败样本。
- 设计理由反复使用“灵活、优雅、可扩展”，却不说明替代方案和代价。
- 讨论区回复高度同质化，大家收藏了，却没有人指出具体代码位置或复现结果。

这些信号不证明教程一定错误，但提醒我降低结论强度：先读仓库、跑最小例子、记录版本，再把“作者的设计解释”与“我实际验证到的行为”分开。

## 我不会直接照搬的部分

- 不会因为帖子被大量收藏，就把教程当成源码审计或生产级设计。
- 不会把“提供 Web / Markdown / PDF”当作内容质量证明，先确认链接和章节是否能访问。
- 不会只读成功路径；没有失败、权限和回滚的 Agent 说明是不完整的。
- 不会把社区里整齐的“mark”回复当成技术验证，它们最多说明标题吸引人。

## 我的阅读结论

Agent 的底层原理并不是更多提示词，而是状态、工具、事件、会话和权限之间的关系。一个教程真正有价值的地方，是让读者能从概念走到代码，再从代码解释取舍和失败。
