我收藏这篇帖子时，标题是“10 章彻底搞懂 Agent 底层原理”。原帖推荐 [dg-ai-notes](https://github.com/buchidonggua/dg-ai-notes)，每章声称同时讲概念、源码和设计原因，还提供 Web、Markdown、PDF 三种阅读方式。

这种介绍很适合让人先收藏，未必能让人学会。评论区有人只留下“先 mark”，也有人觉得文字有明显 AI 味、回复过于整齐。对我来说，这些质疑不是噪音，而是检查教程质量的入口：它有没有让读者看见状态、失败和取舍？

## 每章都问三层问题

| 层次 | 要回答什么                                             | 不能用什么代替   |
| ---- | ------------------------------------------------------ | ---------------- |
| 概念 | Agent Loop、工具、事件、会话和上下文分别解决什么问题？ | “这是核心模块”   |
| 实现 | 状态存在哪里，事件怎样传递，错误怎样返回？             | 只有架构图       |
| 设计 | 为什么这样划边界，失败时如何回滚？                     | “更灵活、更高效” |

只有第一层，教程像术语导览；只有第二层，像代码导读。三层能互相对上，才接近可迁移的原理学习。

## 先画出 Agent Loop

我会把一次可解释的执行压成一个小循环：

```text
读取状态 → 生成下一步动作 → 调用受约束的工具
→ 检查返回值和副作用 → 更新状态
→ 完成、重试，或停下来请求确认
```

教程最容易一笔带过的是“检查返回”和“主动停止”。工具失败时，不能把完整日志塞回模型让它继续猜；要先区分参数、权限、超时，还是外部系统已经发生不可逆变化。超过重试次数或准备改动外部系统时，循环应该停。

## 模块之间必须互相约束

工具系统需要白名单、参数校验、超时、权限等级和结构化错误；读文件、运行测试、改代码、发外部请求不能共享同一权限。事件系统要区分模型想做什么、系统实际做了什么，计划、调用、结果、人工确认和失败原因都应有状态。会话管理要把当前任务、稳定规则、历史摘要和废弃信息分开，压缩上下文后不能丢掉未完成事项和安全边界。审计只记录任务编号、工具名、参数摘要、时间、状态和确认点，不复制密钥或私有文件全文。

## 用五个小任务验证能否落地

1. 只读检索：是否先读规则，再给来源？
2. 单文件修改：是否先说明计划并运行最小验证？
3. 跨文件重构：是否保持范围，不乱改无关文件？
4. 测试失败修复：是否根据结构化错误定位？
5. 外部操作：是否在发送、删除或发布前停下来确认？

这些任务比“回答像不像专家”更能暴露工作台边界。若教程没有失败、超时和回滚示例，我会把它记为概念材料，不把它当成生产方案。

## 怎样判断 AI 味，而不是凭感觉

我会看三个信号：标题反复使用“全面、彻底、从零到精通”，却没有失败样本；设计理由不断说“灵活、优雅、可扩展”，却不交代代价；讨论区回复高度同质化，没有人指出代码位置或复现结果。这些信号不证明教程错误，但提醒我降低结论强度：先读仓库、跑小例子、记录版本，再分开“作者声称的设计”和“我实际验证到的行为”。
