Agent 的难点不在于让模型多说几句话，而在于让它在真实环境中稳定完成任务。一个可维护的 Agent 工作台，至少应该把上下文、规划、工具和审计分开。

## 上下文层

上下文包括任务目标、项目规则、历史结果和当前状态。它应该有边界和优先级，不能把所有文件和聊天记录无差别塞进模型。上下文越清晰，规划越容易复核。

## 规划层

规划层把目标拆成步骤，标记依赖、验收标准和可能的回滚点。对于高风险操作，规划应该先停下来请求人工确认，而不是自动继续。

## 工具层

工具需要白名单、参数校验、超时和权限边界。读文件、运行测试和修改代码的权限不应该默认等价。工具返回的错误要结构化，方便 Agent 修正，而不是把一段长日志原样塞回上下文。

## 审计层

每一次工具调用都应该留下时间、输入摘要、结果和操作者。涉及外部系统的动作要能撤销。审计不是为了监控模型，而是为了在出错时知道发生了什么。

Agent 不是一个更长的提示词，而是一套小型软件系统。把边界和状态设计清楚，才能把偶尔成功的演示变成稳定工作流。

## 审计层要记录什么

审计层不等于把所有内容都复制到日志。它应该记录任务编号、工具名称、参数摘要、开始和结束时间、结果状态以及人工确认点。敏感输入只保存经过处理的摘要，日志本身也应该有保留期限和访问权限。这样发生错误时能定位过程，又不会因为追求“完整记录”把新的隐私风险带进系统。

## Agent 的一次循环

一次可解释的执行循环可以写成：读取状态、提出计划、请求必要工具、检查返回、更新状态、判断是否完成。任何工具失败都要先回到检查状态，而不是把错误原样塞回提示词继续猜。对于超过预估时间、重复失败或即将改变外部系统的动作，循环应主动停止并请求人确认。

## 上下文也需要生命周期

长期运行的工作台不能无限累积聊天记录。可以把内容分成当前任务、稳定规则、历史摘要和已废弃信息，定期压缩并标注来源。每次压缩后保留关键约束和未完成事项，避免 Agent 因为上下文太长而丢掉真正重要的边界。

## 一套最小评测

准备几组固定任务：只读检索、单文件修改、跨文件重构、测试失败修复和需要人工确认的外部操作。观察它是否先读规则、是否给计划、是否按权限调用工具、是否运行验证、失败后是否安全停止。评测过程比单次回答更能说明这个工作台是否值得长期维护。
