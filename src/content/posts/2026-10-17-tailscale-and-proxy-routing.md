组网工具和代理客户端一起使用时，最容易出现“两个界面都显示已连接，但实际访问失败”。原因通常不是某个开关没打开，而是路由、DNS 和流量接管边界没有设计清楚。

## 先理解三条路径

- 互联网流量应该经过代理节点。
- 私有网络流量应该经过组网隧道。
- 本地局域网和特殊保留网段应该按实际需求决定直连还是转发。

如果所有流量都交给一个客户端，排障会变得困难；如果两个客户端都抢默认路由，也会产生冲突。

## 配置时的原则

认证密钥只使用短期、最小权限和可撤销的凭据，不把它写进公开配置或截图。规则按目的拆分，先让少量目标通过，再逐步扩大范围。DNS 解析也要确认是由哪一层负责，避免域名解析成功但连接走错路径。

## 不要只用 ping 判断

有些隧道或代理栈不转发 ICMP，`ping` 失败并不代表 TCP 服务一定不可达。排障时应该使用真实业务端口进行低风险测试，例如确认 SSH 或 Web 服务是否能建立连接，同时查看客户端的路由命中记录。

## 验证顺序

先看设备是否加入同一网络，再看域名解析结果，然后确认目标网段命中了预期规则，最后用真实业务连接验证。每次只改变一条规则，避免路由表被多个修改同时污染。

网络配置的目标不是“所有东西都能通”，而是每一类流量都能解释为什么走这条路，以及出错时能快速撤销。

## 先画出意图路由表

配置前先写三行意图：哪些流量必须经过代理，哪些私有地址必须走组网，哪些局域网地址应该直连。再把意图映射到实际网卡、DNS 和规则。这样两个客户端同时修改默认路由时，能看出它们到底争抢了哪一个出口。

| 目标     | 期望路径       | 需要验证     |
| -------- | -------------- | ------------ |
| 公网域名 | 代理出口       | DNS 与 HTTPS |
| 私有服务 | 组网隧道       | 路由与 ACL   |
| 本地设备 | 直连或明确转发 | 局域网可达性 |

## 按协议逐层验证

`ping` 只能说明某个地址在一种协议下有响应，不能证明 DNS、TCP、HTTPS 和应用层都走了正确路径。我会按顺序检查域名解析、路由选择、目标端口、TLS 和应用返回内容。每一步都保留一条结果，避免把“能 ping”当成完整验收。

## 修改要能回滚

每次只改一组规则，先保存原配置，再用少量目标验证。发现全局网络异常时，优先恢复默认路由和 DNS，不要继续叠加例外规则。认证凭据使用短期、最小权限和可撤销的方式，配置文件和截图都不应出现完整密钥。

稳定不是两个客户端都显示“已连接”，而是重启、切换网络和断开其中一个客户端后，其他流量仍然符合预期。把这些动作加入验收清单，才有机会发现只在启动顺序特殊时才出现的隐性冲突。
