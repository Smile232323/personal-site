设备列表已经出现自己和远端机器，延迟也有了，浏览器却打不开 NAS。这条 Tailscale 集成帖就是从这个反差开始往下查的。

作者想把 Tailscale 和日常代理放进同一个客户端，不必访问私有服务时换一次、访问公网时再换回来。配置完成后，节点显示在线，实际流量却没走通。他在 [#8 楼](https://linux.do/t/topic/2817884/8) 回顾，最后发现通用设置里还藏着一层规则。

这比“重新生成一个密钥试试”更接近问题。登录进 Tailnet 和把一条业务连接送到目标机器，中间还隔着路由、DNS、访问权限与服务本身。

## 节点在线，究竟证明了哪一步

原帖把客户端的设备列表当作连接状态的第一项检查：新节点出现，还能看见其他设备。它能帮助确认登录和节点信息交换，但不能证明所有应用流量都进入了这条通道。

假设手机要打开远端的一项 Web 服务，请求先得离开浏览器，经过系统路由，再匹配客户端规则，才可能进入 Tailnet。目标机器收到连接以后，还要有对应端口的服务在监听。列表中的“已连接”并没有替这些环节逐项签收。

所以排查时，先把目标写得具体一点：哪台设备、域名还是地址、哪个端口、应当由谁接管。只说“内网不通”，很容易同时改了 DNS、节点授权和代理规则，最后不知道哪一步起了作用。

## 最容易漏看的，是规则之前的旁路

作者遇到的问题与 TUN 旁路设置有关。主帖说，当 Tailscale 常用的地址范围被列入旁路，系统可能先把目标连接交给普通网关，没有送进代理客户端的虚拟网络入口。

这时，客户端内部即使写了 Tailnet 分流规则，也可能根本看不到那条请求。继续把同一条规则复制三次，不会改变更早一步的去向。

这里有一个需要保留的条件：原帖是在解释作者当时的配置，不能推成所有客户端版本都默认旁路同一个网段。先看自己的生效配置与路由结果，再判断有没有冲突。Tailscale 常用的共享地址范围也不等于整段地址都属于自己的 Tailnet，不宜仅凭网段名字批量删除其他规则。

一条有用的对照是：用域名访问失败时，再检查其解析出的目标地址；用地址访问也失败时，查这条地址连接有没有出现在客户端记录里。若客户端完全没有收到它，优先查系统接管与旁路；若收到了却选了公网代理，才去查分流规则。

这张图最清楚的一处，是把公网代理、国内直连和 Tailnet 流量分开列了出来。它讨论的是 Android 上用 FlClash/Mihomo 统一接管，而不是同时启动两套 VPN。

图里的脚本既增加 Tailscale outbound，也把相应规则放到前面。只有一个节点定义，没有规则把请求交给它，节点就可能一直闲着；只有地址规则，没有对应的 outbound，也不会凭空得到一条 Tailnet 通道。

另一个细节是域名。用地址访问和用主机名访问，可能命中不同规则。截图提醒，如果只匹配地址，主机名请求仍有可能落到后面的默认代理策略。要验证实际去向，应看请求详情里选中的策略，不能因为配置文件出现了“Tailscale”这个词就算完成。

图片长，手机上可以点开放大看。但复制脚本前，还需要确认当前内核支持该类型、客户端确实运行了覆写脚本，而且规则进入了最终生效配置。截图只是一个方案，不是所有叫 Clash 的客户端都具备相同能力。

## iPhone、Android 和 Mac，不能混成一次验证

主帖以 Shadowrocket 集成为主。[#5 楼](https://linux.do/t/topic/2817884/5) 问功能是否只在测试版，作者在 [#6 楼](https://linux.do/t/topic/2817884/6) 说，自己从 App Store 下载的正式版可以使用。这个回答给了当时的获取渠道，却没有提供精确版本号。

随后 [#9 楼](https://linux.do/t/topic/2817884/9) 问 macOS 的另一个 Clash 客户端能不能参考，作者在 [#10 楼](https://linux.do/t/topic/2817884/10) 明确说没试过。这个“没试过”应该留下来，不能在重写时变成跨平台配置教程。

在需要单一 VPN 接管的移动设备上，把两种能力放进一个客户端有实际意义；在其他系统上，多套网络组件能否共存，还要看它们怎样修改路由和 DNS。排障时先把接管关系简化到可解释的一套，确认后再逐项加回，比同时开着几个客户端猜冲突容易。

这里的目标是减少变量，不是断言任何系统都不能同时运行两个网络工具。

## 密钥过期，也要分清是哪一种

评论 [#11 楼](https://linux.do/t/topic/2817884/11) 觉得 Auth Key 的有效期麻烦，偏好另一款客户端的接入方式。这是很实际的维护成本，但“认证密钥到期”和“已加入设备立即掉线”并不是一件事。

我在整理时核对了 [Tailscale 的 Auth Keys 文档](https://tailscale.com/kb/1085/auth-keys)。官方说明，Auth Key 过期后，已经由它授权的设备仍保持授权，直到设备自己的 node key 过期。需要重新使用一个过期的 Auth Key 注册设备时，才要生成新 key。

因此，断线时不妨先分辨：是新客户端不能注册，还是原来的节点已经在线但业务不通？前者看认证状态，后者先看设备密钥、访问权限和连接路径。把所有故障都归到“密钥过期”，会绕回与实际连接无关的设置。

可复用认证方式是否合适，也取决于要加入几台设备、由谁维护。为了照教程操作，不必把所有认证选项都开到最宽；先明确用途更容易管理。

## 别为了修 ping，把已经能用的连接改坏

主帖还提到一种容易误判的现象：ping 不通，Web 或 SSH 却已经能用。某些客户端或网络策略对 ICMP 的处理与 TCP、UDP 不同，所以单个 ping 结果不能替代业务测试。

可以按用途做一组短检查：主机名是否解析到预期目标；连接有没有被正确的组件接管；目标端口是否可达；最后是否返回需要的页面或 SSH 响应。端口通了但页面不对，还要看服务、证书或主机名配置，而不是继续改 Tailnet 分流。

修改时保存原配置，每次只动一处。验证成功后，再试重连、切换网络和重启客户端，看路径是否仍一致。如果私有服务恢复了，公网却坏了，应先回退这一轮改动，把两个结果分开查。

我想从这条帖留下的，不是一份一键粘贴配置，而是两个位置：请求有没有进入接管组件，进入以后又命中了谁。把这两处看清，设备列表的在线状态才不会被误当成业务已经可用。
