桌面端 Codex 适合浏览、审阅和管理任务，真正的编译、测试和运行环境却常常在远端 Linux。SSH 连接能力把这两件事接在了一起：桌面端负责交互，远端负责代码、依赖和验证。

## 远程工作台需要什么

远端机器至少要准备好四件事：稳定的 SSH 登录、可用的 Codex CLI、项目依赖和能访问模型 provider 的网络环境。桌面端能连上 SSH，只代表通道建立，不代表远端 Codex 已经可以工作。

建议先用普通 SSH 登录远端，再在远端单独确认 CLI 能启动、当前目录正确、Node/Python 等运行时可用。最后才从桌面端连接，减少变量。

## 最容易忽略的配置一致性

官方账号登录和第三方 provider 可能使用不同的模型提供方标识。两边配置不一致时，历史会话、模型名称和额度表现可能不一致。切换 provider 后，桌面端控制的远程服务也可能仍然使用旧配置。

处理这类问题时，先让 CLI 单独成功运行，再重启远程服务，最后重新连接桌面端。不要在桌面端和远端同时修改多套配置。

## 远端不能直接联网怎么办

远端没有公网访问能力时，可以考虑让它通过受控代理或 SSH 通道访问外部服务。这里的重点是让代理边界清晰：哪些流量必须走代理，哪些流量应该直连，凭据放在哪里，失效后如何撤销。

不要把本机完整代理配置或长期密钥直接复制到服务器。更稳妥的做法是使用最小权限、短期凭据和明确的环境变量，并在任务结束后清理。

## 最小验证清单

- SSH 能稳定连接，且使用的是预期用户。
- 远端工作目录和项目权限正确。
- Codex CLI 能单独完成一次无副作用的请求。
- provider、模型和额度配置一致。
- 代理只覆盖需要的流量。
- 编译和测试在远端实际运行过。

远程开发的关键不是“连上了”，而是桌面交互、远端环境、网络和验证结果都能被复现。

## 把远程工作台拆成四次验收

第一步只验收普通 SSH 登录：用户名、密钥、主机指纹和默认 shell 都要符合预期。第二步在远端直接运行 CLI，确认版本、当前目录、Node 或 Python 运行时和项目依赖。第三步单独验证远端到模型服务的网络，不把桌面端能打开网页当成远端已经联网。第四步才从桌面端建立工作台连接，并运行一个不会修改文件的读取任务。

这样的顺序能把问题定位在一个很小的范围。如果第一步失败，不需要看模型配置；如果第二步失败，不需要怀疑桌面端；如果第三步失败，就把注意力放回远端代理、DNS 或出口策略。每一步都通过后再进入下一步，远程开发就不再是“连接成功但什么都不能做”的黑盒。

## 远程工作台的权限边界

桌面端和远端共享的是任务上下文，不应该共享所有权限。项目目录可以给工作账户读写，系统目录、凭据目录和其他用户目录应该保持隔离。运行测试的账户也不必拥有重启服务或修改防火墙的权限。需要部署时，让 Agent 先输出计划和变更列表，再由人执行高风险动作，或者通过最小权限的发布脚本完成。

我还会为远程服务设置明确的停止条件：连续失败次数、超时、磁盘空间不足和依赖版本变化都应该让任务回到安全状态。远端日志要能看出哪次会话、哪个工作目录、执行了什么动作，但不要把 token 或完整环境变量写入日志。

## 连接后的验收清单

- 读取项目规则，确认工作目录正确；
- 修改一个临时文件并撤销，验证权限边界；
- 运行最小测试，确认工具链可用；
- 断开再连接，确认状态不会依赖一次性缓存；
- 检查日志中没有凭据和私人主机信息。

远程开发真正稳定的标志不是“能连上”，而是连接断开、网络变化或任务失败后，仍然知道从哪一层恢复。
