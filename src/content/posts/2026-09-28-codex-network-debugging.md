Codex 突然无法联网时，最容易犯的错误是立刻重装客户端、切换模型，或者反复登录账号。很多时候，问题发生在更靠前的网络链路上：启动脚本没有继承代理变量，系统代理没有接管终端，或者代理已经连通但 provider 不可用。

## 先把问题拆成四层

可以把一次请求看成四层链路：

1. **进程层**：Codex 是否从你预期的 shell 或桌面环境启动。
2. **网络层**：代理变量、系统代理、TUN 或 VPN 是否实际生效。
3. **鉴权层**：账号、provider、额度和模型权限是否可用。
4. **工具层**：模型能否继续访问项目目录、SSH 和外部工具。

从第一层开始检查，能避免把网络问题误判成模型问题。

## 我遇到的根因

我曾经在 shell 里给 Codex 写了一个启动函数。函数为了清理环境变量，顺手删除了所有代理变量，导致终端里的 Codex 请求没有经过本地代理。浏览器和其他应用仍然正常，所以一开始很难想到是启动函数造成的。

修复方式不是增加更多代理，而是让启动入口保持一致：确认 Codex 继承了正确的代理环境，并且没有被别的脚本再次覆盖。

## 推荐的检查顺序

先确认当前进程实际看到的环境变量，再确认代理监听端口是否可用。接着检查 TUN 或系统代理是否接管了终端流量。网络层确认后，再检查 provider、模型权限和额度。最后才看 Codex 的工具调用、项目目录和远程服务。

每一步都只验证一个假设，并记录“现象—命令—结果—结论”，不要一次改很多配置。

## 一个值得保留的习惯

把排障结果写成最小卡片：问题、环境、链路、根因、修复、后续风险。下次遇到相同问题时，先复用卡片，而不是重新搜索一遍。

网络通了并不等于 API 一定可用。代理层成功后，如果 provider 没有可用账号或额度，请把它当成新的鉴权问题处理。
