AI 生成代码已经从补全函数走到了读仓库、拆任务、改多文件和运行测试。变化很快，但工程现场的判断没有被替代：一段代码能被生成，不等于它满足需求，更不等于团队愿意长期维护。

## 先看任务的影响范围

我会把任务放进“影响范围 × 验证成本”的四格里，而不是先问模型够不够聪明。

| 类型             | 适合的协作方式                                  |
| ---------------- | ----------------------------------------------- |
| 影响小、容易验证 | 让 Agent 直接做格式化、重命名、补测试或文档整理 |
| 影响小、难验证   | 先补测试和样例，再让 Agent 改动                 |
| 影响大、可以回滚 | 先要计划和补丁，分小步提交                      |
| 影响大、不可逆   | 只让 Agent 做分析和检查，执行由人确认           |

这个分类比“AI 能不能写代码”更接近工程现场。权限、数据迁移、生产部署和账号变更，即使看起来只有几行代码，也应该按高影响任务处理。

## 一个可复查的协作循环

我通常把一次协作分成五个停顿点：先读仓库规则和入口；再写出小计划和非目标；然后一次只改一块；每一步运行与改动对应的验证；最后由人看差异和风险。计划里要写清楚哪些文件不应该被碰，避免模型顺手做大范围重排。

提交前我会看四件事：改了哪些文件，差异规模是否合理，测试是否覆盖真实入口，有没有凭据、构建产物或无关格式化混进来。一次协作对应一个清晰提交，出了问题才容易回滚和解释。

## 失败时先停，不要让错误扩散

Agent 误解需求后，最危险的不是第一次改错，而是为了修复继续扩大改动。测试失败时，要求它报告失败发生在哪一步、已经改变什么、下一步准备验证什么，然后回到最小复现。保留原始状态和中间差异，比让它连续尝试十个方案更容易控制。

## 评价长期价值，而不是演示速度

我会记录返工率、回滚次数、测试覆盖变化和人工审查时间。一次很顺的演示不能代表长期效率；如果代码越来越难读，生成速度越快，维护债务积累得越快。成熟的 Agent 应该让团队更容易理解和验证代码，而不是把关键判断藏在聊天记录里。

看到“几乎不用手写代码”的展示，我会追问四个问题：改动影响了哪些文件？失败后能否回滚？测试是否覆盖真实入口？半年后别人能否读懂这次决定？只有这些问题都有证据，生成速度才有工程意义。
