作者已经写好了识图 Skill：单独测试能用，放进实际任务却没来得及调用，任务就报错结束了。

他当时在 OpenCode Go 中使用 DeepSeek v4 Flash。平常处理文本任务没问题，遇到图片就卡住；更麻烦的是，有些任务会自己截图验证，用户并没有主动传图，也会在执行到一半时中断。作者想继续保留这个主力模型，于是尝试让套餐里的 MiMo v2.5 负责看图。

这和“给模型多写几条看图指令”不是同一个问题。请求在进入工具选择之前已经失败，再好的指令也还没轮到执行。

## Skill 和 MCP 为什么都可能来不及

评论 [#4 楼](https://linux.do/t/topic/2713829/4) 提出，可以做成 MCP，需要视觉时再调用。作者在 [#8 楼](https://linux.do/t/topic/2713829/8) 回答：他遇到的情况是模型收到图片就报错，没机会再去调用工具。

我觉得这组问答比附件里的启动方式更值得保留。它先把两种失败分开了：一种是模型已经开始工作，只是缺少某项工具；另一种是请求本身不能被当前链路接受。前者可以讨论如何调用识图服务，后者要先改变图片进入系统的位置。

因此，不能把作者的失败扩大成“Skill 或 MCP 都不能识图”。如果主模型只收到图片文件的位置，由另一个工具读取文件，可能走的是另一条路；如果输入里直接带着它不接受的图片内容，工具还没启动就可能出错。具体能否这样编排，要看客户端怎样传递图片，不能仅凭工具名字判断。

评论 [#13 楼](https://linux.do/t/topic/2713829/13) 还建议把视觉任务交给多模态子代理。这也是一种分工，但仍有同样的前提：负责派活的一侧必须先能继续运行，或者事先把视觉步骤安排好，不能等已经失败的请求自己恢复。

## 作者最后改的是请求入口

原帖采用本地代理，把原来的模型请求先接到本机，再接入识图模型。下面这张日志把几个角色写得很清楚。

![原帖本地代理启动日志，列出本机监听地址、上游模型接口、MiMo v2.5 识图模型和客户端 Base URL 修改提示](/personal-site/media/posts/deepseek-vision-01.png)

_来源：[原帖 #1 楼](https://linux.do/t/topic/2713829/1)。这里是模型 API 的本地适配代理，不是浏览器上网用的系统代理。_

日志里有监听地址、上游接口和识图模型，说明客户端与上游之间多了一层处理。它没有告诉我们每次请求经过了哪些分支，也不能单凭“代理已启动”证明所有图片都会被正确转换。

要把这种方案接进自己的工作，最好分别确认：客户端有没有把请求发到这里；代理有没有识别出图片；视觉步骤有没有产生可用描述；后续文本任务有没有拿到那份描述。某一步失败时，返回对应错误，比继续给出一段看似完整的答案更容易排查。

![原帖客户端配置页，模型接口的 Base URL 指向本地代理，认证字段以圆点遮蔽，另有独立的 Proxy URL 字段](/personal-site/media/posts/deepseek-vision-03.png)

_来源：[原帖 #1 楼](https://linux.do/t/topic/2713829/1)，保留原图已有的认证遮蔽。_

这张图还有个容易混淆的地方：Base URL 和 Proxy URL 是两个不同字段。前者决定请求交给哪个模型服务入口，后者关系到连接怎么出去。为了补视觉能力，作者改的是模型请求入口；把浏览器代理端口填进去，并不会自动得到同样的适配功能。

同样，截图中的端口只是作者当时的例子。已有服务占用了那个端口时，应使用实际启动日志给出的地址，不必为了照着图片操作，把其他服务停掉。

## 识图截图里，能确认的比标题少一点

![原帖识图对话，先提取一张帖子截图的文字，再描述测试图中的绿色矩形、橙色圆形和两行文字](/personal-site/media/posts/deepseek-vision-02.png)

_来源：[原帖 #1 楼](https://linux.do/t/topic/2713829/1)。这是作者展示的识图结果，不包含完整请求日志。_

作者用截图文字和一张简单的几何图展示了效果。后一个回答说出了绿色矩形、橙色圆形与两行文字，还提到测试文件。至少从界面上看，对话没有像前面描述的那样立即中断。

但截图中的回答也声称自己“直接读取图片”，不需要再运行 fallback 脚本。这里值得留一个问号：界面显示的主模型名称、回答对自身能力的描述、真正处理图片的后端，不一定能靠这一张图区分。要确认兜底是否触发，还是得看代理记录，不能只听模型说自己怎样完成了任务。

而且，几何图很适合检查有没有走通，不适合检验复杂理解。读出一个圆形，不等于能保住密集表格的行列关系；抄出标题，也不能说明它会正确理解页面布局。

## 两个模型传话，细节可能在中间丢掉

评论 [#9 楼](https://linux.do/t/topic/2713829/9) 更倾向直接使用多模态模型，担心外接识图模型传话时出现理解偏差。作者在 [#12 楼](https://linux.do/t/topic/2713829/12) 则解释，他主要想做兜底，避免任务自动截图时整个流程报错退出。

两人的目标其实不同。偶尔读一张验证截图，和连续理解复杂界面，对视觉链路的要求不会一样。

比如读图表时，视觉模型若只说“曲线整体上升”，后面的文本模型就没法知道单位、误差线和局部转折；分析流程图时，只列出节点名字，却丢了箭头方向，也会把关系说错。针对这些材料，应先要求保留文字、位置和连接关系，再做解释。看不清的数字就留下缺口，重新取局部图，比在传话过程中猜一个值更可靠。

这里的模型选择还受到作者当时套餐与价格的影响。评论有人推荐直接换多模态主力，作者认为更贵；这是他在 2026 年 8 月的取舍，不是现在所有账号都适用的价格比较。

## 验收时，把“没中断”和“看对了”分开

可以先用三种短任务检查：纯文字请求是否仍能正常完成；带清晰文字和图形的图片是否被读取；一张刻意模糊的小图是否会得到“无法确认”的反馈。再让任务跑到需要截图验证的位置，看看原来中断的环节是否真的过去了。

每次留下输入、可核对的预期、实际回答和经过的模型。若图片已经读错，却只检查最终答复有没有生成，链路看起来会很稳定，错误也会稳定地传到下一步。

这条帖给我的启发是一个很具体的排查位置：先看失败发生在输入阶段还是工具阶段，再决定该改哪里。作者的本地代理是其中一种解法，识图质量、模型路由和后续任务仍需要各自验收。
